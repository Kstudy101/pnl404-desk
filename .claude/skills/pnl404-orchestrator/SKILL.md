# PNL404 작업 조율

## 실행 모드: 에이전트 팀

여러 영역에 걸친 작업은 구현 담당과 검증 담당이 결과를 교환하는 팀으로 수행한다.
단일 파일의 작은 수정은 리더가 해당 스킬을 직접 적용해 처리한다.
현재 환경의 도구·권한·동시 실행 한도가 아래 런타임 예시보다 우선한다.

| 담당 | 정의 | 작업 스킬 | 기본 소유 범위 |
|---|---|---|---|
| 화면 | [pnl404-ui](../../agents/pnl404-ui.md) | [pnl404-ui](../pnl404-ui/SKILL.md) | 셸, 전광판 HTML |
| 데이터·게시 | [pnl404-data](../../agents/pnl404-data.md) | [pnl404-publish](../pnl404-publish/SKILL.md) | 갱신 스크립트, 생성 산출물 |
| 검증 | [pnl404-qa](../../agents/pnl404-qa.md) | [pnl404-verify](../pnl404-verify/SKILL.md) | 읽기·검사, 배정된 검사 파일 |

## Phase 1: 컨텍스트 확인

1. 사용자 요청과 후속 메시지, `git status --short`, 관련 차이를 읽는다. 초기 작업·후속 수정·실패 단계 재실행을 구별한다.
2. [프로젝트 지도](references/project-map.md)에서 해당 경계만 읽고 현재 소스로 확인한다. 그래프 도구를 쓸 때는 파일별 coverage를 확인하고 제외·누락 파일을 직접 읽는다.
3. 완료 기준과 수정 파일 소유자를 정한다. `package.json`, README, 하네스 파일은 기본적으로 리더가 편집한다. 같은 파일을 둘에게 배정하지 않는다.
4. 기존 요청이 허용한 작업을 진행한다. 단순 검사 요청에 재계산·배포를 포함하지 않는다. 명시된 배포 요청을 불필요하게 다시 확인하지 않는다.
5. 팀 작업의 기록은 저장소 루트 기준 `_workspace/harness/<실행ID>/`에 보존한다. 절대 경로를 전달한다. 새 작업은 새 폴더, 후속 작업은 해당 실행을 사용한다. 폴더를 일괄 이동·삭제하지 않는다.

## 에이전트 배정 전 스킬 탐색

에이전트를 새로 생성하거나 기존 에이전트에게 새로운 작업을 배정하기 전에, 리더가 [skills.sh](https://skills.sh/)와 [SkillsMP](https://skillsmp.com/) 두 곳에서 해당 작업에 맞는 스킬을 검색한다. 같은 작업의 수정·재검증은 기존 검색 기록을 재사용할 수 있고, 역할·기술·범위가 바뀌면 다시 검색한다.

1. 작업 목적·기술 스택·검증 대상을 검색어로 정한다. skills.sh 목록과 필요 시 `npx skills find <검색어>`를 확인하고 SkillsMP도 별도로 검색한다.
2. 후보의 원본 저장소와 `SKILL.md`를 읽는다. 작업 적합성, 실제 지침, 유지보수 상태, 필요한 도구·권한을 확인한다. 설치 수·별 수만으로 선택하지 않는다.
3. 해당 역할의 프로젝트 스킬과 함께 사용할 외부 스킬을 선택한다. 기존 스킬과 충돌하는 지침은 사용자 요청과 현재 도구·권한에 맞게 적용 범위를 명시한다. 설치 없이 읽어 적용할 수 있으면 그 경로를 사용한다.
4. `01_plan.md`에 두 사이트의 검색어·확인 시각·후보 링크·선정/제외 이유·실제로 읽은 원문 경로를 기록한다. 해당 스킬이 없거나 사이트 접근이 실패하면 그 사실과 대체 근거를 남기고 기존 프로젝트 스킬로 가능한 작업을 계속한다. 검색·설치·실행 여부를 구분한다.
5. 배정 메시지에 역할 정의, 프로젝트 스킬, 선정한 외부 스킬 원문 경로, 적용 범위와 소유 파일을 함께 전달한다. 담당자는 지정 스킬을 읽은 뒤 구현하고 결과 보고서에 적용 내용을 남긴다.

## Phase 2: 구현과 점진적 검증

리더는 `01_plan.md`에 요청, 완료 기준, 담당/소유 파일, 의존성, 상태를 짧게 기록한다.
소유권이 분리된 구현만 병렬화한다. QA는 완성된 모듈과 그 생산자·소비자를 즉시 확인한다.

- Codex에 `collaboration.spawn_agent`가 있으면 정의 파일 경로, 입력, 소유 파일, 결과 절대 경로를 전달한다. `send_message`로 경계 변경·수정 요청을 교환하고 리더가 계획 파일 상태를 관리한다. 등록되지 않은 커스텀 `agent_type`을 가정하지 말고 제공된 기본 실행 역할을 사용하며 현재 모델을 상속한다.
- Claude에서 실제 제공되는 `TeamCreate`/`TaskCreate`/`SendMessage`가 있으면 팀과 의존 작업을 등록한다. `Agent` 호출 시 역할 파일을 읽게 하고 `model: "opus"`를 명시한다. 도구 스키마는 현재 설명을 따른다.
- 팀 도구가 없으면 리더가 같은 역할을 순서대로 수행하고 독립 검증이 아니었다고 기록한다. 존재하지 않는 도구나 모델로 실행을 가장하지 않는다.
- 위임 시 공유 저장소에서 다른 사람의 변경을 되돌리지 말라는 지침을 포함한다. 결과는 `02_ui_result.md`, `02_data_result.md`로 전달하고 QA는 `03_qa_result.md`에 근거를 남긴다. 사용하지 않은 역할 파일은 만들지 않는다.

## Phase 3: 통합과 완료

1. 결과와 실제 diff를 대조한다. `npm run check`를 실행한다. 검사기를 바꿨으면 `npm test`도 실행한다. 화면 변경은 verify 스킬의 해당 상호작용을 실제 브라우저에서 확인한다.
2. 실패는 해당 소유자에게 재현 절차와 함께 돌려보낸다. 최대 2회 수정·검증 후에도 남으면 원인과 미완료 범위를 보고한다. 필수 검증 실패를 통과로 바꾸어 배포하지 않는다.
3. 배포 요청이 있으면 publish 스킬의 준비·배포·확인 절차를 이어서 수행한다. 로컬 검사 완료와 운영 반영 완료를 구분한다.
4. 팀 상태를 마무리하고 `_workspace/` 기록을 보존한다. 변경 내용, 검증 결과, 남은 제약을 간결하게 보고한다.

## 에러 핸들링

도구의 일시적 실패는 상태 확인 후 1회 재시도한다. 재실패 시 가능한 독립 작업을 계속하고 필수 미완료를 밝힌다.
상충 결과는 양쪽 근거를 보존해 리더가 소스로 판단한다. 필수 입력이 없으면 그 입력에 의존하는 갱신·배포를 진행하지 않는다.
이전 실행을 재개할 때 현재 diff와 입력 변경을 다시 확인하고, 실패한 단계 및 영향을 받는 후속 검사만 수행한다.

## 테스트 시나리오

- 정상: “모바일 탭 간격을 줄여줘” → 화면 담당이 셸만 수정 → QA가 세 탭·직접 URL·뒤로가기를 확인 → 오프라인 검사 → 결과 보고.
- 경계: “전광판 상세 점수가 안 떠” → JSON components와 `.toFixed()` 소비 코드를 함께 확인 → 데이터 또는 화면 소유자에게 수정 배정 → 해당 항목을 재검증.
- 실패: “최신 데이터로 갱신해줘”인데 이웃 원본이 없음 → `npm run check:sources`에서 누락 확인 → 기존 산출물을 보존하고 정확한 경로 보고. 최신화 성공으로 기록하지 않는다.
- 후속: “아까 것에서 SOP만 다시 확인” → 이전 결과를 읽고 SOP 관련 검사만 수행한다. 전체 publish를 자동 실행하지 않는다.
- 새 배정: “전광판 모바일 접근성 검증 담당을 배정해줘” → skills.sh·SkillsMP에서 관련 스킬 검색 → 원본 SKILL.md 검토·선정 근거 기록 → 프로젝트 verify 스킬과 함께 전달 → 실제 검사 근거 보고.
- 탐색 실패: 한 스킬 사이트가 접근 불가 → 실패와 다른 사이트의 후보/원문 근거를 기록 → 검색 성공으로 꾸미지 않고 기존 프로젝트 스킬로 가능한 작업을 이어간다.

## 유지보수

역할·스킬 변경 시 중복 여부와 링크를 확인하고 `CLAUDE.md`의 변경 이력을 갱신한다.
의존성 없는 검사기가 읽을 수 있도록 frontmatter의 name은 파일·폴더명과 일치시키고 description은 큰따옴표로 감싼 한 줄 문자열로 유지한다. 새 역할은 위 구성 표에, 역할별 스킬은 해당 정의 파일에 링크한다.
실제 반복 오류나 사용자 피드백이 있을 때 해당 절차를 좁게 수정한다. 선택 기준 평가는 [행동 평가 사례](references/evals.json)를 사용한다. 이는 모델 행동 평가 입력이며 단순 문자열 검사로 자동 선택 정확도를 주장하지 않는다.
